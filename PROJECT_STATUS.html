Phase 2 — Servers (NIP-29 Groups) ✅ COMPLETE

Current state: NIP-29 backend fully implemented and compiled. Frontend Servers.tsx queries live kind:39000 group metadata, createGroup/joinGroup/leaveGroup/postGroupMessage in services/groups.ts, and ServerDetailPage subscribes to kind:9 channel messages with #h filter.

What needs to be done

  1. Frontend — Query real groups
    • Subscribe to kind:39000 (group metadata) to populate the server list instead of MOCK_SERVERS.
    • Each group metadata event has tags: ["h", "group-id"], ["name", "Group Name"], ["description", "..."], ["picture", "url"].
    • Display member count by querying group_members table (or counting kind:9000 add-user events).
  2. Join Server flow
    • User clicks "Join Server" → publish kind:9021 (join request) with ["h", "group-id"] tag.
    • Server (Go relay) receives it, validates via nip29.CheckPermission(), inserts into group_members as "member".
    • Alternatively, if group is open, client can self-join by publishing kind:9000 (add-user) with their own pubkey.
  3. Channel messages (kind 9)
    • Inside a server, subscribe to kind:9 with #h tag filter for that group ID.
    • Composer publishes kind:9 with ["h", "group-id"] tag.
    • Backend validates sender is member before storing.
  4. Server creation (kind 9007)
    • Publish kind:9007 with group ID. Backend inserts into groups table, sets creator as owner.

Backend schema already supports this

-- groups table
CREATE TABLE groups (id TEXT PRIMARY KEY, name TEXT, description TEXT, created_by BYTEA, created_at TIMESTAMPTZ);

-- group_members table
CREATE TABLE group_members (group_id TEXT, pubkey BYTEA, role TEXT DEFAULT 'member', joined_at TIMESTAMPTZ);

-- group_bans table
CREATE TABLE group_bans (group_id TEXT, pubkey BYTEA, banned_at TIMESTAMPTZ);

Security invariant

All NIP-29 permission checks MUST be in nip29.CheckPermission() (server-side). The frontend must never trust its own role claim. The relay already enforces this for group events.

Phase 4 security decisions

  • NWC secrets are encrypted at rest with AES-GCM; the key is a non-extractable IndexedDB CryptoKey. No plaintext connection string is stored or logged.
  • Cashu mints are curated — arbitrary mint URLs are rejected by assertCuratedMint().
  • Widgets are opaque-origin — the sandbox omits allow-same-origin, so storage/cookies are unreachable, and only allow-scripts is granted.
  • Zaps use NIP-57 receipts — the receipt carries bolt11, preimage and the original zap request so clients can verify payment.
  • Relay abuse is throttled — the token bucket rejects clients before the WebSocket upgrade.

Phase 5 security decisions

  • DMs are NIP-17 only — rumor (14) → seal (13) → gift wrap (1059), all NIP-44. NIP-04 is not implemented anywhere.
  • Private keys stay in the signer — NIP-07 delegates encryption/decryption; the app never reads an nsec.
  • Broadcasts are read-only — the view only subscribes to kind:9 by group ID; posting still goes through the server-side NIP-29 permission check.
  • Self-hosted relay is explicit — the local relay is added only when the user enables it in Settings.
